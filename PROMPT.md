## 2. Что мы строим

**Продукт:** SaaS бот-менеджер для Telegram — один бот, который подключается к тысячам чатов, групп и каналов и полностью управляет ими: модерация, анти-спам, капча, статистика, вовлечение, автопостинг. Продаётся по подписке (Free / Pro / Business / White Label).

**Бизнес-модель:** владелец чата добавляет бота в свой чат → настраивает его через админ-панель (Telegram Mini App) → бесплатно получает базовую модерацию → платит за Pro-функции через Telegram Stars или CryptoBot.

**Ключевое отличие от конкурентов (Rose, Combot, ChatKeeper):**
- Настройка через удобный Mini App, а не команды в чате
- ИИ-модерация по смыслу (токсичность, скрытая реклама, скам), а не только стоп-слова
- Кросс-бан база скамеров, общая для всех подключённых чатов (сетевой эффект)
- Полная RU/EN локализация
- White Label: возможность поднять копию бота под брендом клиента

## 4. Архитектурные требования

1. **Мультитенантность с первого дня.** Один инстанс бота обслуживает тысячи чатов. Все сущности привязаны к `chat_id`. Настройки каждого чата — отдельная запись, кэшируются в Redis (`cashews`, тег `chat:{id}`), инвалидация при изменении из Mini App или команды.
2. **Модульность.** Каждая фича (анти-спам, капча, приветствие, статистика и т.д.) — отдельный Python-пакет-плагин с единым интерфейсом:
   ```python
   class BotModule(Protocol):
       name: str
       required_plan: Plan
       config_model: type[BaseModel]      # дефолты — в самой модели
       router: Router                      # aiogram Router модуля
       commands: Sequence[BotCommandSpec]
       miniapp_section: MiniAppSection | None
   ```
   Модули регистрируются в едином `ModuleRegistry`, включаются/выключаются per-chat. Доступность модуля зависит от тарифа чата. Роутер модуля не подключается к диспетчеру напрямую — все апдейты проходят через outer-middleware, который проверяет `enabled` и тариф.
3. **Порядок middleware в aiogram (строго):** дедупликация апдейтов → логирующий контекст → загрузка `ChatContext` (настройки + тариф из кэша) → троттлинг → проверка глобального бана → гейт капчи (read-only до прохождения) → контент-фильтры → стоп-слова / анти-флуд → ИИ-модерация → роутеры модулей.
4. **Feature gating по тарифам.** Единый слой: `await features.has(chat_id, Feature.STATS)`; тариф хранится в БД, результат кэшируется. При даунгрейде Pro-модули мягко отключаются, конфиги сохраняются в БД и восстанавливаются при повторной оплате.
5. **Отложенные действия только через ARQ.** Никаких `asyncio.sleep` / `create_task` для мутов, банов, автоудаления и постов — всё через персистентные джобы с явным `_job_id` (идемпотентность + возможность отмены), переживающие рестарт.
6. **Rate limiting и защита от лимитов Telegram API:** централизованный `MessageSender` с очередью исходящих и приоритетами (модерация > триггеры > рассылки), глобальный лимит ~30 msg/s и ~20 msg/min на группу через Redis token-bucket, обработка `TelegramRetryAfter` с уважением `retry_after`, экспоненциальный backoff и dead-letter для неотправленного.
7. **Безопасность Mini App:** валидация подписи `initData` (HMAC-SHA256 от `WebAppData`-секрета), проверка `auth_date` (TTL ≤ 24 ч), защита от replay; затем выпуск короткоживущего JWT сессии API. Проверка, что пользователь реально админ чата, — через `getChatMember` с кэшем на 5 минут. Все write-эндпоинты — только для админов конкретного чата.
8. **Слои и структура кода:** `router/handler` (тонкий) → `service` (доменная логика, тестируется без Telegram) → `repository` (SQLAlchemy). Транзакции — через `async_sessionmaker` + Unit of Work в middleware/`Depends`. Доменная логика не знает про aiogram и FastAPI.

**Структура монорепо:**

```
apps/
  bot/          # aiogram-приложение (polling/webhook), точка входа
  api/          # FastAPI: REST для Mini App + webhook'и платежей
  worker/       # ARQ worker + cron-джобы
  miniapp/      # React + TS + Vite (единственный JS-пакет)
packages/
  core/         # доменные сервисы: модули, feature gating, тарифы, модерация, наказания
  db/           # SQLAlchemy-модели, репозитории, Alembic-миграции
  shared/       # Pydantic-схемы, enum'ы, константы тарифов, парсинг времени, утилиты
  i18n/         # locales/{ru,en}/*.ftl + рантайм-обёртки для Python и TS
infra/
  docker/       # Dockerfile'ы, docker-compose.yml, .env.example
```

Python-пакеты подключаются друг к другу как workspace-зависимости `uv`; `apps/*` не импортируют друг друга напрямую — только через `packages/*`.

## 5. Функциональные модули (полная спецификация)

### 5.1 Модерация (Free)
- Команды: `/ban`, `/unban`, `/kick`, `/mute [время]`, `/unmute`, `/warn`, `/unwarn`, `/del` — работают ответом на сообщение и по `@username`. Время в формате `30m`, `2h`, `7d` (отдельная тестируемая функция парсинга).
- Система варнов: настраиваемый лимит (по умолчанию 3), настраиваемое наказание при достижении (мут N часов / бан), срок жизни варна.
- Стоп-слова: свои списки per-chat + подключаемые пресеты (мат RU/EN, крипто-скам, казино/беттинг). Действие на выбор: удалить / удалить+варн / удалить+мут. Матчинг — предкомпилированные структуры (Aho-Corasick или скомпилированные regex), кэш на чат.
- Фильтры контента (каждый вкл/выкл): ссылки, `@`-упоминания, форварды из каналов, фото, видео, GIF, стикеры, войсы, кружки, документы, сообщения от имени каналов.
- Анти-флуд: N сообщений за M секунд → мут; отдельный лимит на стикеры/GIF. Счётчики — в Redis (sliding window), без обращений к БД на каждое сообщение.
- Лог-канал: все действия модерации (кто, кого, за что, когда) отправляются в приватный канал админов.

### 5.2 Вход в чат (Free)
- Капча: кнопка / выбор эмодзи / математический пример. Таймаут N минут → кик (ARQ-джоба). До прохождения — read-only (`restrict_chat_member`).
- Приветствие: текст с переменными `{name}`, `{chat}`, `{rules_link}`, медиа, inline-кнопки; автоудаление через N минут.
- Автобан свежерегов: аккаунт без username/фото или подозрительный ID → опционально бан или доп. капча.
- Анти-рейд: при заходе N аккаунтов за M секунд — автоматическое включение режима «только чтение» для новых + алерт админам.
- Обязательная подписка на канал: проверка membership перед разрешением писать (Pro).

### 5.3 Статистика (Pro)
- Счётчики: сообщения по дням/часам, уникальные активные пользователи, топ-10 участников, прирост/отток участников.
- Запись событий — батчами: буфер в Redis → periodic ARQ-джоба → `COPY`/`executemany` в Postgres. Никаких синхронных `INSERT` на каждое сообщение.
- Агрегация: сырые события → почасовые/дневные агрегаты (cron-джоба ARQ), сырые данные старше 30 дней удаляются (партиционирование по дате или batched delete).
- Дашборд в Mini App: графики за 7/30/90 дней.
- Отчёты владельцу в ЛС: ежедневная/еженедельная сводка (настраивается).

### 5.4 Вовлечение (Pro)
- Репутация: `+`, «спасибо» в ответ на сообщение → +1 rep; топ недели/месяца; анти-накрутка (лимиты, нельзя себе).
- Уровни: очки за активность, настраиваемые титулы уровней, команда `/rank`.
- Триггеры: админ задаёт «фраза → ответ» (точное совпадение / содержит / regex), ответ с медиа и кнопками, лимит количества по тарифу. Пользовательские regex компилируются с таймаутом/ограничением длины — защита от ReDoS.
- Автопостинг: посты по расписанию (cron-выражение или «каждый день в HH:MM», с таймзоной чата), с медиа и кнопками, в чат или канал; исполнение — ARQ-джобы.

### 5.5 ИИ-модерация (Business)
- Каждое сообщение (с семплированием и кэшем по хэшу текста для экономии) → классификация: `toxic | hidden_ad | scam | ok` + confidence.
- Настраиваемые пороги и действия per-chat: только алерт админам / удалить / удалить+варн.
- Детект скрытой рекламы и «фейковой поддержки» (типовой крипто-скам).
- Бюджет-контроль: лимит ИИ-проверок в день по тарифу (счётчик в Redis), graceful degradation при недоступности провайдера (circuit breaker, таймауты, fallback на обычные фильтры — сообщения не теряются).
- Провайдер за `Protocol`-интерфейсом: `async def classify(self, text: str, ctx: ModerationContext) -> Verdict`. В тестах — фейковая реализация, без сети.

### 5.6 Кросс-бан база (Business)
- Глобальный чёрный список: пользователь, забаненный за скам в N+ чатах (порог настраивается глобально), помечается.
- Чат может включить: автобан из глобального списка при входе / только предупреждение админам.
- Апелляции: глобальная разблокировка только оператором платформы (супер-админка).

### 5.7 Mini App (админ-панель)
- Список чатов пользователя, где он админ и бот подключён.
- Per-chat разделы: Модерация, Вход, Фильтры, Триггеры, Автопостинг, Статистика, ИИ, Тариф.
- Каждая настройка применяется мгновенно (PATCH → инвалидация кэша чата → бот подхватывает без рестарта).
- Раздел оплаты: выбор тарифа, оплата Stars/CryptoBot, история платежей, автопродление.
- RU/EN переключение, тёмная/светлая тема из Telegram `themeParams`.
- Все запросы к API идут через сгенерированный из OpenAPI типизированный клиент.

### 5.8 Платежи и тарифы

| Тариф | Модули |
| --- | --- |
| Free | Модерация, капча, приветствие, стоп-слова, анти-флуд, лог-канал |
| Pro | + статистика, триггеры, автопостинг, репутация/уровни, обязательная подписка |
| Business | + ИИ-модерация, кросс-бан база, сетки чатов (общие настройки), приоритет |

- Подписка per-chat, помесячно. Stars — через нативный `sendInvoice` (`XTR`) + `pre_checkout_query` + `successful_payment`; CryptoBot — через их API + webhook.
- За 3 дня до окончания — напоминание владельцу (ARQ cron). После окончания — 3 дня grace period, затем даунгрейд на Free.
- Обработка платежей идемпотентна: уникальный индекс по `(provider, provider_payment_id)`, повторный webhook не создаёт второй платёж и не продлевает подписку дважды.

### 5.9 Супер-админка платформы
- Отдельные команды/панель для оператора: список всех чатов, тарифы, выручка, управление глобальным бан-листом, бродкаст владельцам чатов (через приоритетную очередь рассылки с учётом лимитов).

## 6. Модель данных (минимум, расширяй по необходимости)

`Chat` (id, tg_chat_id, title, type, plan, plan_expires_at, owner_tg_id, settings JSONB), `ChatModuleConfig` (chat_id, module, enabled, config JSONB), `Warn`, `Punishment` (тип, до какого времени, arq_job_id), `TriggerRule`, `ScheduledPost`, `StatEvent` → `StatDaily`, `Reputation`, `GlobalBan` (tg_user_id, reason, chat_count), `Payment` (provider, provider_payment_id, amount, currency, status, chat_id, period), `AdminUser` (tg_user_id, chat_id, role).

Напиши **полные SQLAlchemy 2.0 модели** (declarative, `Mapped[...]` / `mapped_column`, `DeclarativeBase`) и соответствующую **начальную Alembic-миграцию** с индексами: уникальный по `tg_chat_id`, составные `(chat_id, tg_user_id)`, `(chat_id, created_at)` для статистики, частичные индексы для активных наказаний, GIN по JSONB там, где по нему фильтруем. Все `datetime` — timezone-aware UTC.

## 7. Нефункциональные требования

- `mypy --strict` проходит без ошибок, `ruff check` и `ruff format` — чисто. Никаких `Any` и `# type: ignore` без комментария с причиной.
- Никакого блокирующего I/O в асинхронном коде; CPU-тяжёлое (компиляция больших списков стоп-слов и т.п.) — через `asyncio.to_thread`.
- Все тексты бота и Mini App — через i18n (RU/EN), никаких хардкод-строк. Язык ответа = язык чата (настройка), fallback — `language_code` пользователя, затем EN.
- Graceful shutdown: остановить приём апдейтов, дождаться обработки текущих, дождаться/переоткрыть ARQ-джобы, закрыть пулы БД и Redis.
- Идемпотентность обработки апдейтов (дедуп по `update_id` в Redis) и платёжных webhook'ов.
- Юнит-тесты на критичную логику: варны, feature gating, парсинг времени (`30m`/`2h`/`7d`), анти-флуд, валидация `initData`, идемпотентность платежей. Интеграционные — на testcontainers.
- `README.md` с полной инструкцией запуска (`docker compose up` → работает), описанием ENV и командами `task` для dev-режима.

## 9. Формат работы

- Перед началом каждого этапа кратко опиши план (файлы, решения) и сразу приступай к коду. Не задавай вопросов, если ответ можно вывести из этого ТЗ — принимай разумное решение и фиксируй его в комментарии `# DECISION:`.
- Пиши полный рабочий код файлов, не псевдокод и не «...остальное аналогично».
- Если файл длинный — всё равно пиши его целиком.
- Соблюдай единый стиль ошибок: доменные исключения (`DomainError` и наследники) → человекочитаемые ответы бота на языке чата; в API — единый exception handler → RFC7807-подобный JSON.
